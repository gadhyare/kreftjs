# أمان حزم npm وخيار السماح أو الرفض

يفحص Kreft الحزمة وشجرة اعتمادياتها قبل تثبيتها في مشروعك. بعد اجتياز سياسة الأمان يعرض النتيجة، ثم يطلب منك اختيار **السماح (Allow)** أو **الرفض (Disallow)**. تختار السماح أو الرفض لهذه المرة، أو حفظ قاعدة تسمح بالإصدار الذي فُحص أو تمنع الحزمة في المشروع. لا تتجاوز القواعد المحفوظة سياسة الأمان. لا يعني اجتياز الفحص أن الشيفرة خالية من جميع المخاطر.

## تثبيت الحزم وفحصها

الأوامر `kreft install` و`kreft i` و`kreft add` تستخدم المسار نفسه لحزم سجل npm:

```bash
kreft install luxon
kreft i luxon@3.7.2
kreft add -D vitest
kreft install luxon --check
kreft install luxon --check --json
kreft install luxon --dir ./my-app
```

## قائمة اختيار مثل إنشاء تطبيق جديد

مثل سؤال JavaScript أو TypeScript عند تشغيل `kreft new test-app`، يعرض تثبيت الحزم قائمة مرقمة بعد اكتمال الفحص الأمني. تظهر القائمة مع `kreft add dayjs` أو `kreft i dayjs` أو `kreft install dayjs`:

```text
Security checks passed for dayjs@1.11.23. Choose what to do:
  1) Allow installation once
  2) Disallow installation once (default)
  3) Always allow this package in this project
  4) Never allow this package in this project

Installation [1/2/3/4]:
```

رقم الإصدار المعروض هو الإصدار الدقيق الذي حُلّ أثناء العملية، وليس رقمًا ثابتًا.

- **1 — السماح مرة واحدة:** يثبت الحزمة بعد اجتياز السياسة، دون حفظ قاعدة. يظهر السؤال مجددًا في المرة التالية. تُقبل أيضًا الإجابات `a` و`allow` و`y` و`yes`.
- **2 — الرفض مرة واحدة:** يلغي التثبيت دون تغيير ملفات المشروع أو كتابة تقرير جديد. هذا هو الافتراضي عند الضغط على Enter أو إدخال إجابة غير معروفة أو إغلاق الإدخال أو الضغط على Ctrl+C. تُقبل أيضًا `d` و`disallow`.
- **3 — السماح المحفوظ:** يثبت الحزمة ويحفظ الإصدار الذي فُحص، مثل `dayjs@1.11.23`، في `security.allowedPackages`. عند طلب الإصدار نفسه لاحقًا يعاد الفحص، ثم يُتجاوز السؤال فقط إن نجح. تُقبل أيضًا `r` و`always`.
- **4 — المنع المحفوظ:** يلغي التثبيت ويحفظ اسم الحزمة، مثل `dayjs`، في `security.deniedPackages` لمنع جميع إصداراتها مستقبلًا. تُقبل أيضًا `n` و`never`.

عند طلب عدة حزم، يخص القرار العملية كلها؛ رفضها يلغي تثبيتها جميعًا. تُحفظ القواعد للحزم المطلوبة فقط، ولا تمثل موافقة تلقائية على اعتمادياتها. لا يظهر السؤال للحزم المحظورة أو للفحص الجاف. يتجاوز المشروع السؤال للحزم المسموح بها مسبقًا بعد نجاح الفحص الكامل فقط.

الفحص يستخدم السجل وقد يحدّث ذاكرة npm المؤقتة وسجلاته خارج المشروع. عند اختيار 2 تبقى ملفات `package.json` و`package-lock.json` و`node_modules` والإعدادات والتقارير السابقة دون تغيير، ويُحذف المجلد المؤقت. الخياران 3 و4 يكتبان القاعدة في ملف إعدادات المشروع. تظهر أثناء الفحص حالة التقدم وملخص النتائج، ويمكن استخدام `--verbose` لعرض التفاصيل لكل حزمة.

## الاستخدام في CI

استخدم موافقة صريحة في البيئات غير التفاعلية:

```bash
kreft install luxon --yes
kreft install luxon --check --json
```

الخيار `--yes`، واختصاره `-y`، يسمح بالتثبيت بعد اجتياز الفحوص فقط. لا يتجاوز الحظر. تستطيع أيضًا الإجابة عن القائمة في طرفية المحرر أو عبر إدخال موجّه. عند غياب الإدخال أو إغلاقه تظهر رسالة إلغاء واضحة؛ استخدم `--yes` للتثبيت الآلي دون سؤال. يعيد الحظر أو الرفض أو فشل التثبيت رمز خروج غير صفري. يكتب `--json` تقرير JSON إلى stdout والتشخيصات إلى stderr؛ لا يحتاج الفحص الجاف إلى موافقة.

## مراحل الفحص والتثبيت

ينشئ المثبّت مجلدًا مؤقتًا داخل المشروع، وينسخ إليه ملف الحزم والقفل وإعدادات `.npmrc`. يحل npm شجرة الاعتماديات مع تعطيل السكربتات، ثم يفحص Kreft كل إدخال في ملف القفل، بما فيه الاعتماديات المتعدية والاختيارية والنظيرة والإصدارات المكررة. يتولى npm تعارضات الإصدارات والعلاقات الدائرية، وتبقى إعدادات السجل الخاص والنطاقات سارية.

تتضمن الأدلة اسم الحزمة وإصدارها المطابق تمامًا والرابط إلى ملفها وقيمة سلامتها، وبيانات الرخصة والمشرفين والمستودع عند توفرها، ونتيجة خدمة التنبيهات الأمنية. تُطلب البيانات الوصفية مرة واحدة لكل حزمة وإصدار أثناء العملية، مع مهلات وإعادة محاولات محدودة. الادعاءات المنشورة في السجل ليست إثباتًا مستقلًا لسلامة الناشر.

بعد اجتياز السياسة وموافقتك، ينفذ المثبّت `npm ci --ignore-scripts` في المجلد المؤقت. يتحقق npm من بايتات الحزم وفق قيم السلامة، ثم يقارن Kreft ملف القفل وهويات الحزم المثبتة بالشجرة المعتمدة. يسجل الاعتماديات الاختيارية التي لم تُثبت على المنصة الحالية. لا يجلب `--check` ملفات الحزم للتحقق من بايتاتها؛ الموافقة في التقرير الجاف هي موافقة على الأدلة والسياسة فقط.

عند نجاح التحقق يستبدل المثبّت شجرة `node_modules` بالشجرة المعتمدة ويحدّث ملف الحزم والقفل مع حفظ الإصدارات المباشرة بدقة. تُزال الحزم الزائدة والتعديلات اليدوية داخل `node_modules`. يستعيد الملفات السابقة عند فشل النقل المعتاد، لكن انقطاع الجهاز أثناء نقل عدة ملفات قد يستدعي استعادة يدوية من مجلد `.kreft-node-modules-*`.

## تصنيفات الأمان

- **موثوق Trusted، المستوى 1:** يحتاج إلى دليل منشأ موثّق تشفيريًا لا يوفره التنفيذ الحالي؛ لذلك لا يمنح Kreft هذا التصنيف. اشتراط المستوى 1 يمنع التثبيت حاليًا.
- **راسخ Established، المستوى 2:** بيانات هوية وسلامة متطابقة مع السجل، ونتائج تنبيهات متاحة، ودليل رخصة، وبيانات مشرف ومستودع افتراضيًا. لا يمثل ضمانًا لسلامة الشيفرة.
- **غير متحقق Unverified، المستوى 3:** أدلة ناقصة أو حزمة مهجورة أو تعبير رخصة يحتاج إلى مراجعة. يمكن السماح به صراحة في السياسة، لكن غياب بيانات السجل أو التنبيهات يظل محظورًا افتراضيًا.
- **محظور Blocked:** فشل شرط إلزامي مثل ثغرة عالية أو حرجة وفق الإعدادات، أو رخصة ممنوعة، أو حزمة مدرجة في قائمة المنع، أو اختلاف في الهوية أو السلامة.

لا تمنح كثرة التنزيلات أو انعدام الاعتماديات تصنيف الثقة. لا يُحظر الإصدار لمجرد عمره، ولا يعني غياب التنبيهات عدم وجود ثغرات. معلومات المنشأ المعلنة تُسجّل بوصفها غير متحققة.

## إعداد سياسة المشروع

أضف `security` إلى إعدادات المشروع الحالية دون حذف إعداداتك الأخرى. يستخدم Kreft آلية البحث الحالية لملف `kreftjs.config.json`، بما فيها مجلدا `config/` و`Config/` والأسماء القديمة المدعومة:

```json
{
  "security": {
    "enabled": true,
    "minimumTier": 2,
    "blockCriticalVulnerabilities": true,
    "blockHighVulnerabilities": true,
    "blockMaliciousPackages": true,
    "ignoreScripts": true,
    "verifyIntegrity": true,
    "auditOnInstall": true,
    "allowUnverified": false,
    "checkDependencies": true,
    "checkLicenses": true,
    "checkMaintenance": true,
    "failOnUnknownSecurityStatus": true,
    "deniedLicenses": ["AGPL-3.0-only"],
    "deniedPackages": ["example-denied", "another-package@1.0.0"],
    "allowedPackages": ["dayjs@1.11.23"],
    "reports": {
      "enabled": true,
      "format": ["json", "text"],
      "directory": ".kreft/security"
    }
  }
}
```

القوائم `deniedLicenses` و`deniedPackages` و`allowedPackages` فارغة افتراضيًا؛ القيم أعلاه مثال لسياسة خاصة بالمؤسسة. الإعدادات الأخرى في المثال هي القيم الافتراضية. تُرفض المفاتيح غير المعروفة والأنواع غير الصحيحة. يجب إبقاء `enabled` و`ignoreScripts` و`verifyIntegrity` و`checkDependencies` على `true` في التنفيذ الحالي.

للسماح بالمستوى 3 اضبط `allowUnverified: true` أو `minimumTier: 3`. يظل اشتراط المستوى 1 قائمًا ولا تتجاوزه هذه الموافقة. غياب البيانات المطلوبة يظل محظورًا مع `failOnUnknownSecurityStatus: true`. تعطيل التدقيق دون تغيير هذا الشرط يؤدي إلى الحظر بسبب غياب الأدلة. تفحص قائمة الرخص الممنوعة معرفات SPDX بصورة محافظة حتى داخل تعبيرات OR، ولا تختار رخصة بديلة تلقائيًا ولا تقدم تفسيرًا قانونيًا.

## إدارة القرارات المحفوظة

الخيار 3 يحفظ الإصدار الدقيق الذي وافقت عليه، والخيار 4 يمنع جميع الإصدارات بالاسم. يمكنك تعديل القواعد دون تثبيت حزم:

```bash
kreft install --allow-package dayjs@1.11.23
kreft install --allow-package @scope/tool
kreft install --deny-package dayjs
kreft install --forget-package dayjs
kreft install --packages
kreft install --packages --json
```

يقبل الإدخال اسم حزمة لجميع الإصدارات أو اسمًا مع إصدار دقيق، ولا يقبل نطاقًا أو وسمًا أو رابطًا. حذف قاعدة بالاسم عبر `--forget-package` يزيل قواعد جميع إصداراتها. السماح الصريح يزيل قواعد المنع المتعارضة، والمنع الصريح يزيل السماح المتعارض؛ أما ملف إعدادات يسمح ويمنع الحزمة نفسها بإصدارات متداخلة فيُرفض.

تُحفظ القواعد في ملف إعدادات المشروع الموجود، مع إبقاء الإعدادات الأخرى وقيم `${NAME}`. الإعداد المحفوظ لا يغيّر قواعد الثغرات أو الرخص أو السلامة أو المستوى، ولا يمنح الحزمة تصنيف Trusted. إن تعذر الحفظ يعرض Kreft رسالة، ويظل القرار صالحًا للعملية الحالية فقط. شارك ملف الإعدادات مع الفريق إذا أردت مشاركة القواعد.

## التقارير وتشخيص النتائج

الملفان الافتراضيان هما:

```text
.kreft/security/latest.json
.kreft/security/latest.txt
```

تستبدل العمليات التي تكتب تقريرًا الملفات السابقة. الإلغاء لا يكتب تقريرًا جديدًا ولا يحذف تقريرًا قديمًا. يتضمن التقرير الحزم وإصداراتها ومواقعها في الشجرة، والأدلة والتحذيرات وأسباب المنع والتنبيهات ذات الصلة، والسياسة المستخدمة. يسجل القرار التفاعلي في `decision` بالقيمة `allow` أو `disallow`؛ وقد تصبح `status` مساوية لـ `installed` أو `cancelled` أو `blocked` أو `failed`، وتبقى `approved` للفحص الناجح دون تثبيت. عند الرفض بعد اجتياز السياسة يسجل التقرير في الذاكرة `policyAllowed: true` لتمييز قرار المطور من الحظر الأمني. يسجل `decisionSource` مصدر القرار: `prompt` أو `allowedPackages`، ويظهر الحفظ في `remembered`. عند الإلغاء لا تحفظ ملفات التقرير، لكن `--json` يطبعه إلى stdout.

احمِ التقارير إن كان مشروعك يستخدم حزمًا خاصة لأنها قد تتضمن بياناتها الوصفية. استخدم `reports.enabled` لتعطيل حفظ الملفات، أو `reports.format` لاختيار JSON أو النص، أو `reports.directory` لتغيير المجلد داخل المشروع.

## حدود الدعم الحالية

التنفيذ يدعم مشروعات npm المستقلة وملفات القفل بالإصدارين 2 و3. تُرفض aliases ومصادر git والملفات والروابط المباشرة وworkspaces وoverrides وshrinkwrap ومديرو الحزم الآخرون برسالة واضحة. لا توجد بعد خدمة مستقلة لكشف جميع الحزم الخبيثة أو مراجعة شيفرة شاملة أو مقارنة تاريخية لتغير الاعتماديات أو تحقق تشفيري من المنشأ.

تبقى جميع سكربتات دورة التثبيت معطلة، ولا توجد استثناءات لكل حزمة وإصدار بعد. تُرفض الخيارات القديمة `--allow-scripts` و`--trusted` و`--no-audit` و`--no-exact`. الحزم الأصلية التي تحتاج إلى البناء تتطلب خطوة بناء منفصلة بعد مراجعتها. لا يتجاوز `--force` السياسة.

الأمر `kreft add electron tauri` يجهز ملفات سطح المكتب عبر مسار الإعداد الحالي المنفصل؛ لا يشمله فاحص الحزم هذا. نفّذ إعداد سطح المكتب وتثبيت حزم السجل في عمليتين منفصلتين. يسري فاحص الحزم على الاعتماديات المستخدمة في تطبيقات الويب وCapacitor وElectron وTauri، لكنه لا يدقق أدوات المنصات الأصلية نفسها.

## تمرين عملي

شغّل `kreft install luxon --check --json` وافحص التقرير. ثم شغّل التثبيت التفاعلي واختر 2، وتحقق من بقاء ملفات الاعتماديات كما هي. أعد العملية واختر 1، وافحص الإصدار الدقيق في `package.json`. أخيرًا أضف اسم الحزمة إلى `deniedPackages` وأعد الفحص للتأكد من الحظر دون تقديم خيار لتجاوز السياسة.

جرّب الخيار 3 وتحقق من حفظ الإصدار في `security.allowedPackages`، ثم الخيار 4 في مشروع تجريبي آخر وتحقق من حفظ اسم الحزمة في `security.deniedPackages`. استخدم `--forget-package` لإزالة القاعدة وإعادة السؤال.
